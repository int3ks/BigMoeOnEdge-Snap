# BigMoeOnEdge+ Changelog

## Snap fork

- **Fix: no long-press menu on messages with a link.** Text with a URL was drawn with `ClickableText`, which took every gesture on the text, so the bubble's long-press menu (Edit, Regenerate, Copy) never opened there. `LinkedInlineText` (`ui/chat/MessageBody.kt`) now takes only a short tap on a link and leaves everything else to the bubble.
- **Agent actions fold into one line.** A run of tool rounds (calls without answer text and their results) is shown as one row with the latest action and the number of steps ("Reading https://… · 4 steps"); a tap unfolds every call and result as before. Image results stay visible as cards. `ui/chat/ChatScreen.kt` (`groupActions`, `ActionGroupRow`).
- **Web budget per message.** A model re-read the same page about ten times until an 8k context was full (the identical-call stop only comes after 8 rounds). Per user message, a repeated `web_search` (same query) or page read (same URL, spelling-normalized; `extract_webpage` per URL and query) now gets a one-line note instead of the page, at most 2 searches and 3 page reads run (more get "web budget used up, answer now"), and `read_webpage` returns at most a fifth of the free context (~3 chars/token, 500–6000 chars). `core/AgentController.kt`.
- **Auto cores while an answer runs.** Auto decided only before an answer, so a long answer kept its cores however hot or cool the device got. The engine now takes a core change between two tokens (`Session::request_cores`, JNI `nativeRequestCores`): thread counts and cores are set and the persistent compute pools rebuilt there, as at the start of a generation; the graph hook's cores follow (`set_cores_callback`). Auto (`core/AutoCores.kt`) now decides every 2 s from the engine's live counters (`Session::live_decode`: tokens emitted and decode time, prefill excluded): a speed window closes every 48 tokens of one core set; a core is added once the current set has two windows, and the added core's next two windows decide whether it stays (at least 95 % of the speed before, else it goes and adding pauses 5 minutes). Heat steps (throttling, 95 % headroom, the chosen cores coming back) are at least 20 s apart. Host test `live_cores_path` in `session_ckpt_test` (two changes mid-decode, same answer, counters add up).
- **Fix: hang or crash when the compute threads were rebuilt.** The CPU backend kept the pool it computed with last; the session freed its pools after detaching them, and the next graph paused the freed pool (`ggml_threadpool_pause` on freed memory: a hang, as in the host test, or a crash). It could happen before every answer whose thread counts or cores differed from the last one (Auto cores, Settings). `llama_context::detach_threadpool` now makes the backend let go first (`patches/0008-llama-detach-threadpool.patch`).
- **Auto cores: thresholds for the MagicPad.** Under load it sits at about 80 % headroom with status LIGHT, so 7.43 still never added a core. A core is now added below 90 % headroom (status at most LIGHT), an added core goes from 95 %. Throttling (status MODERATE+ or Honor step 3) with added cores in use first only takes those away and blocks adding for 5 minutes; only if it goes on does Auto go below the chosen cores. The chat header also shows Honor's own step ("Honor N"), which blocks adding from 2.
- **Auto cores less conservative: throttle step 1 (LIGHT) no longer counts as heat.** The MagicPad 3 Pro reports thermal status LIGHT permanently, fan or not, so Auto never added a core and took added ones away. A core is now added at status NONE or LIGHT (headroom below 70 %, Honor step below 2), an added core goes only from 85 % headroom; status MODERATE or worse still sheds cores as before.
- **Ask user before the web:** with Ask user on, the web is never used for a message before the user was asked at least once. If the model has not asked a question of its own yet (`ask_user` earlier in the message, or before the web call in the same round), the first web access (`web_search`, `image_search`, `read_webpage`, `extract_webpage`, and the app's own search in "always" mode) waits for a card "May I search the web for …?" / "May I open this web page? …" with "Yes, use the web" and "No, answer without the web" plus the own-answer field. No or Dismiss: no web for the rest of the message, the model is told to answer from its own knowledge; an own answer goes to the model instead of the web results (it may call the tool again). The system prompt now puts `ask_user` before every other tool: ask first when the request leaves open something that changes the result, before searching or starting the work.
- **Ask-user tool (`ask_user`)**: the model can ask the user a question in the middle of an answer, with 2 to 4 answer options. The chat shows a card under the live answer with the question, one button per option, a field for an own answer (Enter or the arrow sends it) and Dismiss; the run waits (no time limit) until the user answers, and the choice or text goes back to the model as the tool result (`The user answered: …`), which then goes on. Dismiss, the tool's cancel button and Stop give the model "the user dismissed the question". Switch in Settings → Tools → Ask user and in the chat's tools menu, per chat; off by default. `tools/AskUserTool.kt` (options also accepted as a string with one per line / `|` / `;`), `ToolManager.questionHandler`, `GenerationManager.pendingQuestion`/`resolveQuestion`, `ui/chat/AskUserCard.kt`. Not offered over the API server (it uses the client's own tools).
- **Auto cores by Android's throttling signals instead of °C.** The two temperature settings are gone: the skin °C was the thermal headroom converted with a scale calibrated on the Honor, wrong on other devices (and Samsung has no "ThermalTempLevel"). Auto now reads `PowerManager.getThermalHeadroom` (1.0 = severe throttling) and `currentThermalStatus` directly: a core is added below 70 % headroom with status NONE, an added core goes from 85 % or status LIGHT, and only status MODERATE or worse (or Honor's own step 3+) goes below the chosen cores. The chat header shows "heat NN %" (and "throttle N" while Android reports throttling) instead of °C.
- **Engine: the calling thread gets the core its pool leaves free.** It computes with the pool's workers but could run on any chosen core, and Android often put it on a worker's core while the free one stayed idle (Galaxy S25 Ultra, 7.39: that worker fell from about 250 % to 125–210 % per 3 s, the answer stuttered at 4 t/s). The graph-compute hook (`llama_set_graph_compute_hook`, now with the graph's thread count and whether the session's pool computes it) now pins the caller to the n-th core of the set for graphs of the pool; graphs without it (ggml's own workers inherit the caller's cores) keep the whole set.
- **Fix for 7.38: the prefill threads all on one core when decode and prefill cores differ.** Building a strict pool pins the calling thread to that pool's own core, and the prefill pool, built right after the decode pool, took its allowed cores from the calling thread: one core, so all its threads ran there (Galaxy S25 Ultra, decode cores 0xdf by Auto, prefill 0xdc: five threads at 20 % each on cpu4, the answer hung in the prefill). The pools now take the allowed cores from the process's main thread.
- **Fix for 7.37: loads and some prompts stacked all compute threads on one core.** 7.37 pinned the calling thread to the one core its pool left free. Graphs without the session's pool (the warm-up of a load, and a 40 s phase before a regenerated answer) make workers that inherit the caller's cores, so all five ran stacked on that core (a load took 89 s instead of about 28 s). The caller is set to the whole core set again; the pool's workers keep one core each and leave it the free one. Measured on the S25 Ultra with 7.37 otherwise: 5.7 and 6.9 t/s, about 0.09 s compute per token (before: 1.2 t/s, 0.77 s), `cores_busy` 5.07 with 5 threads.
- **Engine: one core per compute thread.** The compute threads could move freely over the chosen cores, and Android stacked two of them on one core while another chosen core idled (Galaxy S25 Ultra, logged per thread: two threads at 50 % each for seconds). ggml's threads wait for each other spinning after every operation, hundreds of times per token, so each wait lasted until the scheduler switched the stacked thread in: about 0.75 s compute per token and 1.2 t/s, against about 6 t/s in the phases without stacking, at the same clocks and with almost no page faults. The persistent pools now place strictly (`strict_cpu`, one core per worker, the lowest ones of the mask) and the calling thread takes the remaining core (see the fix above: in 7.37 the graph-compute hook pinned it there); with fewer cores than threads it stays as before.
- **Chat header readable on a phone:** a tap on the chat title no longer unfolds it inside the top bar (its fixed height cut the extra lines off) but shows title and model line in full in a panel below the bar; another tap folds it. **"Forget this chat's saved KV"** moved from the top bar into the ⋮ menu (`NavMenuItem` in `MainNavButtons`, which now shows the ⋮ menu on wide screens too when a page adds entries), so the title keeps more room.
- **Correction to the two entries below (measured on the Galaxy S25 Ultra with 7.36):** the clock cap is Samsung's thermal control (SIOP in `com.sec.android.sdhms`), stepped by the chip (AP) temperature: 49.5 °C → 2.25 GHz, 51.4 °C → 1.96 GHz, 53 °C → 1.69 GHz, while Android's thermal status stays 0 until the last step. It comes without the game category too, and the service cannot be disabled without root (`pm disable-user` is ignored). It also does not decide the speed: an answer reached about 6 t/s at the lowest cap and slowed down at higher clocks. Still open: the app's anonymous memory in zram (about 700 MB, page faults per token between 18 and 2500 from answer to answer) and n-gram drafting.
- **No longer marked as a game (no `android:appCategory`).** On a Galaxy S25 Ultra the decode ran at full clocks (3.5/4.5 GHz) for about 6 s, then Samsung pinned both CPU clusters to about 2 GHz (`scaling_min_freq` = `scaling_max_freq`, stepping 2.0–2.7 GHz every ~10 s) for the rest of the answer, with no heat behind it (thermal status 0). Short answers finished before that and reached 5 t/s, long ones fell to about 1 t/s. Removing the app from the Game Launcher did not help, Android kept it in game mode `performance`. Build with `-PbmoeAppCategory=game` to compare (it helped on an older phone in 0.5.0); it merges `src/appCategory/AndroidManifest.xml`, since `undefined` is no valid manifest value.
- **Engine: persistent compute threads.** No threadpool was attached to the llama context, so ggml created and joined its worker threads for every graph, several times per token. The scheduler never saw a lasting load on them and the CPU governor kept the clocks low (measured on a Galaxy S25 Ultra: 1.15–1.4 of 3.5/4.5 GHz while decoding, 3.5 GHz right after), which made decode speed vary up to 3x between days with the same settings. The session now keeps one ggml threadpool for decode and one for batched graphs (one when both match), shared by the target and the MTP draft context, placed on the decode/prefill cores (`Session::set_cpu_masks`); it is rebuilt at the start of a generation when the thread counts or cores changed (Settings, Auto cores).
- **Auto cores repaired:** the decode cores chosen in Settings are now the minimum; Auto only adds cores on top and takes the added ones away when hot. Only Honor's own throttling (ThermalTempLevel 3+) goes below them (never below 2), and they come back when it stops. `cores_busy` is no longer a criterion (spinning threads count as busy, so a busy set was often the slow one, and prefill-heavy turns looked like idle cores): an added core is kept only if the next answer with 48+ tokens decodes at least 90 % as fast as before, otherwise it is taken back and Auto waits 5 minutes. New thresholds: add below 41.0 / 42.0 °C, take away above 43.0 / 44.0 °C. The run summary JSON now carries `n_generated` and `decode_tps` (`native-bridge.cpp`).
- **Chat button "Forget saved KV of this chat"** (top bar, sweep icon): deletes the chat's KV snapshots on disk (every model setup) and drops the context the engine holds (`Session::forget_kv`, `nativeForgetKv`), so the next message replays the chat with a full prefill. Workaround while nonsense answers after a chat switch are investigated.

- **Fix: a second Regenerate prefilled the whole conversation again** on hybrid models (Qwen3.5/3.6) and after a KV snapshot (MagicPad, 7.04: 12 of 576 tokens reused). When the checkpoint list was full, the eviction rule from upstream #603 dropped every checkpoint an earlier request took within `checkpoint_min_step` (8192) of the one before it, so with 4 kept everything but the preamble's went, including the one 4 tokens before the prompt's end. "Close" is now 16 tokens (`k_checkpoint_close_tokens`): only the pair at a prompt's end is thinned. - **Droppable cache share** (Settings → MoE streaming & I/O, "Droppable cache share (experimental)", default coldest 25 %, 0 = off; `MoeStreamConfig::cache_discard_pct`, `I_CACHE_DISCARD_PCT`): on the MagicPad (7.03, swap off) upstream's discardable cache was far too eager - after any drop it offered everything but the last token's experts and the budget followed every drop down to one token's cycle, so Qwen3.6-35B with an 8500 MiB cache had a low hit rate and slow decode, and the offered pages showed as free RAM. Now only the coldest share of the cache (by last use) is ever offered, and a drop never takes the budget below the rest; the cache brake can still go lower. 100 % = upstream's rule.
- **Sliding-window layers keep only their window in the KV cache** (upstream #580, `swa_full` off): llama.cpp's default gave Gemma's SWA layers a cache as long as the context; now they hold the window plus one ubatch (Gemma 4 26B-A4B at 16k context: context memory about 2.3 GiB → 0.4 GiB upstream; checkpoints copy only the window, so they shrink too). A cut further back than the window (Regenerate or an edit after a long answer) is caught by the sliding-window check added on 2026-11-20 and served from a context checkpoint (now also 4 tokens before each prompt's end) or a full prefill. KV snapshots saved by an older build with the full SWA cache do not fit and are refused; the chat is then replayed as usual. New host test on a tiny gemma4 (window 16, SWA cache 256 cells): follow-up, Regenerate, edit, Regenerate of the first turn and a snapshot round trip all answer exactly as a fresh session (`tests/make_tiny_moe.py` from upstream).
- **Engine fixes and speed-ups from upstream BigMoeOnEdge (0.41–0.46), ported onto the 0.28-based engine:**
  - **A failed expert read ends the run on the serial path too** (#668). Without overlap (the default) a failed read (storage error, a shard cut short, a drive removed) was dropped by the caller: the entry counted as resident, the matmul ran on a slice nobody had read, the answer looked like a success and the entry was served as a hit later. ## Unreleased - NPU prefill + MTP fix

- NPU prefill now works together with Guess ahead (MTP and n-gram). Before, three independent gates refused the combination: `config.cpp` ("prefill.device does not combine with speculative decoding"), `native-bridge.cpp` (rejected any `I_SPEC_SOURCE`) and the Settings switch (`npuCombinationAllowed`). Removing the gates alone would have been unsafe, so the engine was also fixed: the MTP draft pass during prefill ran while the target's weights were rebound to the device (and with the arena hooked in), and the MTP head's layer, experts and KV were pulled into the device rebind. See docs/NPU_MTP_FIX.md.
- The NPU "minimum prompt tokens" threshold must now exceed the speculative verify width (draft_max + 1); the app raises it automatically and the Settings list only offers valid values.
- A separate MTP sidecar GGUF is loaded CPU-only while NPU prefill is on, so it does not open a second HTP session.
- MTP / n-gram Guess ahead can now be loaded together with an mmproj. Before, `session.cpp` refused both at load and on any image turn. Image turns decode plainly (the engine already disabled drafting for them), and both contexts' KV is cleared around them, so text turns afterwards re-prefill target and draft consistently.
- Not compiled with the NDK/Hexagon toolchain and not run on a device in this environment.

## 0.6.0 — 2026-10-23

- **Auto settings** (Settings → top card): scans RAM, CPU cores/fast cores, SoC, a quick memory-speed test and whether the NPU runtime is available, then builds settings for the chosen model in three tiers: **Fastest**, **Balanced** and **Most accurate (slowest)**. MoE and dense models get different plans (expert cache, dropped/substituted experts, prefetch, guess-ahead, context, threads).

- **Saves**: named, switchable (Use), renamable, deletable, and downloadable/importable as small JSON files. Switching a save only changes the engine settings Auto settings owns; sampling, tools and theme are untouched.
- Measuring is crash-guarded: plans are kept inside a cautious RAM budget, a save that wouldn't fit is skipped instead of loaded, only one big load exists at a time, the screen stays on while measuring, and a crash marker lowers a save's memory use automatically if the app is killed mid-measurement. The Fastest tier no longer uses expert substitution, two-wave reads or a wide prediction window (the settings its first version crashed a 35B-A3B model with), and its expert-count cut is milder (8 → 6); older saves are cleaned automatically. NPU prefill is opt-in (off by default). Each save has a "Lower memory" button.
